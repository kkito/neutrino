# 专题：BT 隧道 51413 不通 / transmission 代理配置误判

- **状态**：✅ 已通（重启 transmission 后 TCP+UDP 双隧道均有流量）
- **发现时间**：2026-10-25 06:10（核对线上部署时）
- **影响**：BT 上下行完全静止，`/api/live` 里 `trans-bt` 常年 0，`trans-bt-udp` 干脆不出现
- **是否代码问题**：**不是**。neutrino 侧无缺陷，是传输配置 + 部署状态问题

---

## 1. 现象

核对线上时发现：

| 观测点 | 数值 |
| --- | --- |
| `/api/tunnels` | `trans-bt` / `trans-bt-udp` 都 **online** |
| HK `ss -tlnp` | `0.0.0.0:51413` (tcp) + `0.0.0.0:51413` (udp) 都在听 |
| HK `/dev/tcp/<HK_SERVER>/51413` | ✅ **可连接**（隧道链路是通的） |
| 本机 `172.28.0.10:51413` | ✅ transmission 在听 |
| **`/api/live`** | `trans-bt: rx=0 tx=0`；**`trans-bt-udp` 完全不出现** |
| HK `tcpdump udp port 51413` 15 秒 | **零入站包** |
| transmission 33 个任务 | **全部 `status=0`（已暂停）** |

**关键矛盾**：隧道全 online、端口全通、端到端 TCP 可连，但**双向零流量**。

---

## 2. 根因（三层）

### 2.1 直接原因：33 个任务全部暂停

`torrent-get` 显示所有任务 `status=0`（STOPPED）。暂停的任务不做种也不下载，
自然没有任何 BT 报文 ⇒ `tcpdump` 抓不到包 ⇒ 隧道空闲 ⇒ `/api/live` 全 0。

### 2.2 transmission 只在启动时读 `settings.json`

之前往 `/config/settings.json` 写了 `proxy_url`，但**没有重启容器**。
transmission 4.x 的代理配置是启动时一次性加载的，改动不重启 = 不生效。

重启后：
- 33 个任务从 `status=0` 全部变成 `status=6`（SEED，做种中）
- `trans-bt-udp` **立刻出现在 `/api/live`**
- 两条隧道都开始有双向流量

### 2.3 transmission 4.x 的代理只有 `proxy_url` 一个字段（重要认知纠正）

排查时一度判断「缺 `proxy-enabled` / `proxy-type`，所以代理没开启」——
**这个判断是错的**。用 `transmission-daemon --dump-settings` 拿权威字段名：

```
$ transmission-daemon --dump-settings --config-dir /tmp/dt2 | jq 'keys | map(select(test("proxy")))'
["proxy_url"]         ← 87 个设置项里，只有这一个
```

4.1.1 的 RPC `session-get` 同样返回**零个** `proxy` 字段。

⇒ **`proxy_url` 本身就是开关**：填了走代理，留空不走。
3.x 时代的 `proxy-enabled` / `proxy-type` / `proxy-auth-*` 已被合并掉。
**不要再往 settings.json 里加这些字段**，加了也不会被读取。

### 2.4 `status=5` 不是运行态（自己踩的判读坑）

首次统计时用 `status in (3,4,5)` 当"运行中"，得出结论 `运行中 0/33`，
误以为"启动了又全退回暂停"。实际 transmission 4.x 的状态码：

| 值 | 含义 |
| --- | --- |
| 0 | STOPPED（暂停） |
| 1 | CHECK_WAIT |
| 2 | CHECK |
| 3 | DOWNLOAD_WAIT（排队等下载） |
| 4 | DOWNLOAD |
| 5 | SEED_WAIT（排队等做种） |
| 6 | **SEED（做种中）** ← 100% 完成的任务在这里 |

判据应写 `status in (3,4)` 判下载、`status in (5,6)` 判做种/运行。

---

## 3. 修法

```bash
# transmission 的配置是启动时读的，必须 stop → (改文件) → start
docker stop transmission
#   如需改代理：编辑 /config/settings.json 的 "proxy_url"
docker start transmission
```

本次配置本身已正确（`proxy_url = http://172.28.0.1:18080`），只需重启生效。

任务恢复：

```python
rpc("torrent-start", {"ids": [...]})   # 或 GUI 全选 → 开始
```

## 5. 顺带确认：隧道本身没问题

排查过程中验证了 neutrino 侧完全正常，**不要再去改代码**：

- `/api/tunnels` 两条 51413 隧道 status=online
- HK server 上 TCP/UDP 51413 均监听（同一个 `neutrino` 进程，fd 12/13）
- 从 HK 公网 IP 回连 `<HK_SERVER>:51413` 成功 → 隧道到本机 transmission
- 本机 `172.28.0.10:51413` transmission 侧可达

⇒ 链路「公网 → server → kudus → agent → transmission」每一段都是通的，
**唯一缺的是 transmission 自己不产生流量**。

## 6. 教训

1. **「隧道 online + 端口在听」不等于「有流量」**。排查顺序应该是
   **先看 `/api/live` 有没有字节 → 再抓包看公网有没有包 → 最后才查隧道**。
   这次从隧道侧查起，绕了一大圈。
2. **Docker 服务的配置文件改动必须重启容器**，`docker exec ... > settings.json`
   不会触发热加载。transmission / qbittorrent 这类都是启动读一次。
3. **不要凭 3.x 的印象猜 4.x 的字段名**。`--dump-settings` 是权威来源，
   5 秒就能确认，比翻文档快。
4. **状态码表要先查再写**，`status=5` 是 SEED_WAIT 不是 SEED，
   差点把"全部在正常做种"误判成"全部被暂停"。
5. **没流量先怀疑应用层**，不要一上来就怀疑传输层——这次 neutrino 侧
   一行代码都没问题，但差点又去翻 kudus。
