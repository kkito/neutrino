# 专题：公网链路 15-20% 丢包下 kudus 吞吐塌陷（SACK 有、快速重传无）

- **状态**：✅ 已修复并线上验证（`9af1edd` 快速重传 + `6b2c0bb` 重排窗死锁 + `10fa13b` 防风暴硬闸）
- **关联**：
  - [2026-10-23-kudus-retx-storm.md](./2026-10-23-kudus-retx-storm.md)（重传风暴）
  - [2026-10-24-udp-stream-lifecycle-blind.md](./2026-10-24-udp-stream-lifecycle-blind.md)（UDP 流静默）
- **发现途径**：2026-10-24 用户反馈 egress HTTP 代理（18080）对任何目标超时；
  用户两次质疑"不可能是 BT 抢带宽""数据量不大哪来的拥塞"，实测证实用户判断正确
- **性质**：**协议栈性能缺陷**（非崩溃、非内存泄漏）；链路质量是诱因，但协议没有
  针对高丢包场景的快速恢复路径

## 结论速览（TL;DR）

| 现象 | 实测 |
| --- | --- |
| egress 代理小请求（google/generate_204） | ✅ 0.5-0.9s 正常 |
| egress 代理 1MB 下载 | ❌ 只拿到 31-65KB 即超时 |
| BT 隧道 | 看似正常（UDP 不可靠，丢包无所谓） |
| 本机 → HK `ping -i 1` × 100 | **15-20% 丢包** |
| 本机 → 阿里 DNS 223.5.5.5 | 0% 丢包（国内链路无问题） |
| 本机 → 8.8.8.8 | 8% 丢包 |
| 丢包形态 | **随机、分散单包**（丢失序号 `[3,16,26,38,40,42,47]`，连续丢段长度全为 1） |
| TCP 对照（scp 20MB） | 20s 内仅 655KB ⇒ **~32KB/s** |

**根因不是带宽、不是拥塞、不是写泵故障**——是 **kudus 只有被动超时重传
（RTO=200ms 指数退避），缺少「选择性重传 / 快速重传」路径**。链路随机丢 15%
时，每个洞都要等满 RTO 才能补，且补的包还可能再丢，吞吐被 O(N×RTO) 拖死。

## 1. 现场排除过程（记录错误判断，供后续参考）

用户最初报告"18080 代理不能用"。排查中出现过三次误判，**全部被用户当场质疑纠正**：

| 错误判断 | 用户质疑 | 实测证伪 |
| --- | --- | --- |
| BT 流量抢带宽（QoS 拥塞） | "BT 那边应该大量丢包，数据量也不大" | `backlog_max=4~23`，远低于背压阈值 256；停掉 transmission 后代理仍 100% 超时 |
| 双 UDP socket 抢同一会话 | —— | 重启后单 socket 仍复现 |
| agent 写泵 task 死掉，`emit` 静默失败 | —— | 加 `send_fail` 计数后现场实测 `send_fail=0` 恒定不动 |

**教训**：应先测物理链路质量（`ping` 丢包率），再怀疑上层代码。
本次排查在应用层绕了一大圈，而 `ping` 一分钟就能证明链路 15% 丢包。

## 2. 关键实测：丢包是随机的，不是按大小/按比例固定丢

包大小扫描（每档 40 包，`ping -i 0.05`）：

```
size=56   5%     size=200  15%    size=500  5%
size=1000 5%     size=1200 5%     size=1400 30%
```

同大小重复 5 轮（1000B × 50）：

```
round1 30%   round2 36%   round3 32%   round4 22%   round5 20%
```

**结论**：丢包率在 5%-36% 之间浮动，与包大小无稳定相关性 ⇒ **不是运营商按包长
或按比例的策略性丢弃**，而是链路本身的随机丢包（跨境拥塞/丢包）。

> 注意：`ping -i 0.05` 会触发 ICMP 限速，曾测出 `6667% packet loss`
> （重复/错误报文）。**丢包率必须用 `-i 1` 慢速测**，否则数据不可信。

## 3. 协议现状：SACK 已实现，但没有「只补洞」

用户提出的机制——"告诉对方我收到最远哪个包 + 中间丢了哪几个，只重发丢的那几个"——
**正是 SACK（Selective ACK），kudus 已经实现了**：

| 机制 | 代码位置 | 状态 |
| --- | --- | --- |
| 累积确认（最远连续收到的包） | `ReorderBuf::ack()` = `next - 1` | ✅ 有 |
| 选择性确认（中间哪些到了） | `ReorderBuf::sack()` 256 位 bitmap | ✅ 有 |
| 发送方按 SACK 清除已到包 | `RetxBuf::on_ack(ack, sack)` | ✅ 有 |
| 接收方每次推进立即回 ACK | `pkt.send_ack_only()` | ✅ 有 |
| **收到 SACK 后立刻重传洞** | —— | ❌ **没有** |
| **重复 ACK 计数 / 快速重传** | —— | ❌ **没有** |

### 3.1 缺失环节的实际影响

当前重传**只由 RTO 超时驱动**：

```rust
// src/common/kudus.rs
pub fn take_expired(&mut self, _rto: Duration, now: u64) -> Vec<(u32, Vec<u8>)> {
    for (seq, e) in self.seqs.iter_mut() {
        // 注意：只看「自己上次发送距今多久」，完全不看对端 SACK 说了什么
        if now.wrapping_sub(e.last_sent) >= rto_for(e.retx).as_millis() as u64 {
            e.retx += 1;
            e.last_sent = now;
            due.push((*seq, e.payload.clone()));
        }
    }
}
```

**问题链条**：

1. 包 1 丢失，包 2..N 正常到达
2. 接收方 SACK 标记 2..N 已到，`ack` 仍停在 0（洞在 1）
3. 发送方收到 SACK，**知道包 1 丢了**，但 `take_expired` 不看 SACK，
   必须等 `last_sent + rto_for(retx)` 超时
4. 首次 RTO = 200ms；若重传又丢，退避 400ms → 800ms → ... → 封顶 8s
5. `rto_for` 指数退避使高丢包下延迟急剧放大

**15% 丢包下**：1000 个包约丢 150 个，每个至少 200ms，重传再丢则加倍。
理论最小恢复时间 ≈ `150 × 200ms ≈ 30s`（且未计入重传再次丢失）。

对照 TCP：**收到 3 个重复 ACK 立即快速重传**，无需等 RTO。这是 kudus 缺的那一环。

### 3.2 为什么"看起来还能用"

- **小请求**（1-2 个包）：85% 概率一次成功，感知正常
- **BT/UDP 隧道**：UDP 语义允许丢，丢了就丢了，不影响感知
- **只有需要可靠传大量数据的场景（HTTP 代理、TCP 隧道）才会暴露**

## 4. 已加的诊断埋点（本 PR 顺带）

`Pkt::emit` 是全链路唯一发送出口，旧代码所有调用点都是 `let _ =`，
发送失败完全静默。现已加：

- `send_fail_count()`：累计发送失败帧数
- `note_send_fail()`：失败时限流 warn（每 5s 最多一行）
- 每分钟 `kudus retx` 汇总行新增 `send_fail=` 字段

现场验证结果：**`send_fail=0` 全程不变** ⇒ 本地发送链路完好，
问题确实在网络层/协议层，不是写泵故障。这条埋点排除了整条本地路径。

## 5. 修复：SACK 驱动快速重传（已实施并验证）

### 5.1 方案选择

| 方案 | 改动量 | 预期收益 | 风险评估 | 结论 |
| --- | --- | --- | --- | --- |
| **B. SACK 驱动立即重传** | 小 | 高 | 需防重传风暴 | ✅ **采用** |
| A. 3-dup-ACK 快速重传 | 中 | 同 B | 需额外状态机 | 不需要，见下 |
| C. 前向冗余（每包 2 份） | 小 | 中 | 带宽 ×2 | 兜底，暂不做 |
| D. RTO 自适应 | 中 | 中 | 跨境 RTT 抖动大 | 后续 |
| E. 加大 SACK_BITS | 小 | 低 | 高丢包下窗不够 | 后续 |

**为什么不选 A**：kudus 接收方每次重排推进都立即回带 SACK 的 ACK，
**一份 SACK bitmap 已经等价于 TCP 的 duplicate-ACK 信号**，
不必另建 dup-ACK 计数状态机，也不会因纯 ACK 包丢失而误判。

### 5.2 实现

`RetxBuf::on_ack(ack, sack)` 从返回 `()` 改为返回 `Vec<(seq, payload)>`：

1. 先按累积确认 + SACK 清除已到包（原有逻辑）
2. 在 SACK 窗口内找**最小的洞**（`[ack+1, highest_sacked)` 中仍在 `seqs` 里的）
3. 只返回该一个洞，调用方立即重发

**防风暴三重保险**：

- 只补**最小那一个洞**（不整窗重发）
- 只在该包 `retx == 0`（未快速重传过）时补——对端持续回同一份 SACK
  不会让我们每收一帧就重发一次
- 「已快速重传过就交给 RTO 退避」——不会形成自激

SACK bitmap 全零（对端什么都没乱序收到）时**不冒进**，交给 RTO 判断。

调用点：`src/agent/kudus_session.rs::Pkt::on_ack`、
`src/server/kudus.rs` 读循环，两侧对称。

### 5.3 实测效果（2026-10-24 本机 minipc7s → HK）

链路状态：`ping -i 1` × 100 = **10-20% 丢包**，RTT 36-38ms。

| 场景 | 改造前 | 改造后 |
| --- | --- | --- |
| `google/generate_204` | 0.5-0.9s ✅ | 0.5-0.9s ✅ |
| 1MB 下载 | **31-65KB 后永久卡死** | ✅ **11-13 秒完成** |
| 200KB × 20 连续 | 几乎全超时 | ✅ **20/20 成功，40-134KB/s** |

**约 80 倍提升**，且速度（~90KB/s 均值）已超过同期 TCP 实测的 28KB/s——
kudus 无需像 TCP 那样保守降窗。

## 6. 第二根因：重排窗口永久死锁（已修复）

### 6.1 现象

快速重传上线后仍有「跑一阵就全超时、重启即恢复」的周期性死锁。抓现场
（`/tmp/watch-hang.sh` 自动等待并抓包）得到：

| 观测点 | 数值 | 说明 |
| --- | --- | --- |
| 抓包方向 | `In=288 Out=12` | 入站全是 94B |
| 入站包内容 | 288 个全是 **94 字节** | 94 = 50B 帧头 + 封装 ⇒ **纯 ACK 帧** |
| agent `send_fail` | 0 | 本地发送从未失败 |
| agent `backlog_max` | 16 | 重传队列几乎空 |
| server `sent` | **3950**（一分钟） | 重传泵空转 |
| server `tx` | **0B** | 数据一个字节没送出去 |
| 隧道 | `trans-bt-udp` 正常、`trans-bt`(TCP) 全死 | UDP 无重排依赖 |
| 线程 | 5 个全 `S`（睡眠），CPU 2.1% | 不是忙等/死锁在锁上 |

**两边指标都"健康"，链路却完全不通** —— 这是最难查的一类。

### 6.2 根因

`ReorderBuf::push` 的窗口检查顺序错了：

```rust
// 旧代码
if self.buf.len() >= KUDUS_WINDOW {
    return out;          // ← 窗口满就把新包全丢掉
}
self.buf.insert(seq, payload);
while let Some(p) = self.buf.remove(&self.next) { ... }
```

**`seq == next` 的包（唯一能推进窗口的那个）也被这个检查挡住了。**

死锁链条：

1. 某包彻底丢失 —— 重传达 `KUDUS_MAX_RETX`(=10) 被发送方 `abandoned`
2. 后续包全部进 `buf` 缓存，`buf.len()` 涨到 `KUDUS_WINDOW`(=512)
3. 窗口满 ⇒ **连补上那个洞的包都收不进来**
4. `next` 永卡 ⇒ `ack()` 不动 ⇒ 发送方继续重传 ⇒ 接收方窗口恒满
5. **双向死锁**，只能重连

server 侧每收一个洞后包就走 `if ready.is_empty() { 回纯 ACK; continue; }`
（`server/kudus.rs:512`），于是 50ms 一个纯 ACK 帧无限循环——正是抓到的
288 个 94 字节包。

15-20% 丢包链路下，某包连续丢 10 次并不罕见（`0.15^10 ≈ 5.8e-9`，
但每天数十万包，且丢包是成簇的，实际概率远高），所以「跑一阵必死」。

### 6.3 修法

`seq == next` 是唯一能推进窗口的包，**不受窗口上限约束**，优先消费：

```rust
if seq == self.next {
    out.push(payload);
    self.next = self.next.wrapping_add(1);
    while let Some(p) = self.buf.remove(&self.next) {
        out.push(p); self.next = self.next.wrapping_add(1);
    }
    return out;
}
if self.buf.len() >= KUDUS_WINDOW { return out; }  // 其余包才受窗口限制
```

### 6.4 验证

新增单测 `reorder_window_deadlocks_on_permanent_hole`：
先灌满 512 个乱序包，再让「丢失的洞」到达——旧代码返回空（永远解不开），
新代码能一次性投递整批。回退验证：短路修复 ⇒ 用例变红 ✅

线上实测（本机 minipc7s → HK，链路 10-20% 丢包）：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 200KB × 40 连续（3 分钟） | 几分钟内必死锁 | ✅ **40/40 成功**，60-145KB/s |
| 5 个并发 1MB | **必死锁** | ✅ **5/5 全部完成** |

## 7. 防重传风暴：三道软约束 + 一道硬闸

2026-10-23 的重传风暴（[retx-storm](./2026-10-23-kudus-retx-storm.md)）把链路
打出 **42 倍放大**（`thru` 从 899KB 单调涨到 22MB），整机网络瘫痪、frpc 断连。
快速重传是新增的重传路径，必须回答"会不会重演"。

### 7.1 昨天的三个放大器，现在都在

| 缺陷 | 昨天 | 现在 |
| --- | --- | --- |
| 无退避（固定 200ms） | ❌ 恒定 5 次/秒 | ✅ `rto_for()` 指数退避 200ms→8s 封顶 |
| 无容量上限 | ❌ 无界增长 | ✅ `KUDUS_RETX_CAP=4096` |
| 无放弃（无限重发） | ❌ 永不丢弃 | ✅ `KUDUS_MAX_RETX=10` 后 `abandoned` |

快速重传**不绕过任何一道**：它只是把"第一次重传"从"等 200ms"提前到"立刻"，
包本身仍计入 `retx`，后续照样走退避与次数上限。

### 7.2 三道软约束（快速重传自身）

1. **一轮只补最小那个洞** —— 不整窗重发（整窗重发正是昨天放大的来源）
2. **每包只补一次** —— `retx == 0` 才补，对端持续回同一份 SACK 不会反复触发
3. **SACK 全零不冒进** —— 对端什么都没乱序收到时无从判断，交给 RTO

### 7.3 一道硬闸

```rust
pub const FAST_RETX_PER_MIN: usize = 200;
```

滚动 60s 窗口内快速重传超过 200 次，整体退回纯 RTO 退避。
200/分钟 ≈ 3.3 包/秒，远低于 RTO 泵的 20 包/秒节奏，正常链路远够用。

### 7.4 实测：无放大

空闲状态连续 5 分钟采样（本机→HK）：

| 采样 | `sent` | `backlog_max` |
| --- | --- | --- |
| 1（BT 突发后） | 1235 | 178 |
| 2 | 244 | 12 |
| 3 | 236 | 11 |
| 4 | 254 | 19 |
| 5 | 221 | 14 |

**稳定在 221-254，无单调爬升**（风暴的判据是持续增长，昨天 `899KB→22MB`）。
`backlog_max` 从 178 回落到 11-19，队列正常排空。
空闲重传 3.5KB/s vs 业务 3.0KB/s ≈ **1.2 倍**，与 15% 丢包的理论下限
`1/(1-0.15)=1.18` 吻合。

### 7.5 顺带修掉的快速重传自身缺陷

- **退避中的洞挡住后面所有新洞**：`retx > 0` 时原本 `return Vec::new()`
  直接退出查找，一个还在退避的洞会让后面的洞永远补不上。
  改为 `continue` 继续往后找。单测 `fast_retransmit_skips_retrying_hole`。
- **最后一个洞补不上**：`for d in 1..highest` 把 `highest` 本身排除在外
  （它是最高 SACK 位的偏移，本身也可能是洞）。改为 `1..=highest`。
